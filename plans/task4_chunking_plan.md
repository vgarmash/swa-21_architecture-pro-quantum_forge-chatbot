# План обновления индексации Markdown-документов

## Наблюдения по формату
- Документы оформлены в Markdown, даже при расширении `.txt`.
- Структура повторяется: заголовок уровня `#`, далее блоки `##`, местами вложенные `###`, списки, жирные подписи.
- Встречаются русские и английские маркеры разделов (например, «Глава», «Раздел»), а также структурированные списки.
- Чаще всего документы принадлежат к типам: декреты, энциклопедические заметки, журнальные записи, письма, отчёты, мифы.

## Требования к обновлению
1. Выполнить предварительный анализ содержания на английском (логирование ключевых сведений: заголовок, разделы, количество слов, списки).
2. Сегментировать текст строго по разделам (заголовки `#`, `##`, `###`, а также ключевые слова `Chapter`, `Section`, `Глава`, `Раздел`).
3. Использовать чанкер с размером 200–500 токенов, целевой размер ~400, перекрытие 10–20% (план: 15%).
4. Следить, чтобы чанки заканчивались на границах предложений и сохраняли завершённость мысли.
5. Добавлять в метаданные названия разделов, уровень заголовка, идентификаторы чанков.
6. Пересоздавать хранилище Chroma (полное удаление папки перед построением).
7. По возможности использовать `chonkie.RecursiveChunker` и fallback на кастомную реализацию при отсутствии библиотеки.
8. Адаптировать подсчёт длины чанка под модель `sentence-transformers/all-MiniLM-L6-v2` (использовать оценку по словоформам и настроить параметры под ограничение 512 токенов модели).

## Предлагаемая архитектура
- `load_documents()` — без изменений по чтению, но дополнить базовой нормализацией.
- `analyze_document()` — парсинг Markdown, сбор статистики и логирование на английском.
- `extract_sections()` — разбиение на секции по заголовкам/ключевым словам.
- `chunk_sections()` — для каждой секции деление на чанки с помощью `RecursiveChunker` (если доступен) либо fallback, с контролем перекрытия и границ предложений.
- `prepare_documents_for_index()` — преобразование секций в список объектов [`Document`](task4/m/build_index.py:7) с обновлёнными метаданными.
- `reset_vector_store()` — удаление директории `chroma_db` перед пересозданием индекса.
- `build_index()` — оркестрация: загрузка, анализ, чанкинг, пересоздание Chroma, логирование статистики (количество чанков, средняя длина).

## Проверка и логирование
- Выводить в лог количество исходных документов, секций, чанков, минимальный/максимальный размер чанка.
- Сохранять в метаданных: `source`, `filename`, `section_title`, `section_level`, `chunk_index`, `section_index`, `approx_token_count`.
- Журналировать шаги на английском (как требует постановка задачи).
