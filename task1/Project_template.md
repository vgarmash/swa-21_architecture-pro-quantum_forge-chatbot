# Отчёт по исследованию моделей и инфраструктуры для RAG-бота QuantumForge Software

## Введение и контекст

Задача поставлена техническим руководством QuantumForge Software, финско-эстонской компании, разрабатывающей SaaS-платформу Digital Twin для промышленных клиентов, включая ABB и Wärtsilä. Цель — создать интеллектуального бота для сокращения времени поиска информации сотрудниками, которое сейчас достигает четырёх часов в неделю на человека. Ключевым ограничением является конфиденциальность данных: документация содержит коммерческую тайну, архитектурные решения и спецификации для интеграции с SCADA-системами клиентов. С учётом требований соответствия стандарту SOC 2, передача таких данных в публичные облачные API сторонних вендоров неприемлема. Следовательно, архитектура решения должна обеспечивать полный контроль над информацией внутри инфраструктуры компании.

## 1. Сравнение LLM-моделей

При выборе языковой модели основная дилемма заключается между локальными решениями на базе открытых моделей с Hugging Face и использованием облачных API, таких как OpenAI GPT или YandexGPT.

Облачные модели, в частности GPT-4, демонстрируют наивысшее качество генерации и понимания сложных технических контекстов. Скорость ответа через оптимизированные API составляет 1-3 секунды, что идеально для интерактивного общения. Стоимость является операционной (OPEX) и рассчитывается за токены, что удобно для старта. Однако, для кейса QuantumForge этот путь имеет фатальный недостаток: конфиденциальные данные будут передаваться на серверы третьей стороны, нарушая политики безопасности и делая невозможным прохождение аудитов. Простота развёртывания в этом случае не компенсирует фундаментальный риск утечки.

Локальные модели, такие как Llama 3 70B или CodeLlama 34B, предоставляют полный суверенитет над данными. Их качество для технических задач, особенно CodeLlama для работы с кодом, является высоким, хотя и немного уступает GPT-4 в общих рассуждениях. Скорость работы напрямую зависит от выделенного оборудования: развёртывание на мощных GPU (например, NVIDIA L40S или A100) позволяет достигать времени ответа 2-10 секунд. Стоимость смещается в сторону капитальных затрат (CAPEX) на серверы и их обслуживание, но в долгосрочной перспективе становится предсказуемой. Развёртывание сложнее, требует экспертизы в настройке GPU-инфраструктуры, квантовании моделей и оркестрации, но это единственный жизнеспособный путь для обработки конфиденциальной информации.

Таким образом, для QuantumForge обязательным является выбор локальных LLM. В качестве переходной стратегии на пилотном этапе можно рассчитать использование облачного API (например, GPT-3.5 Turbo) только для запросов, которые проходят предварительную проверку и классифицируются как не содержащие чувствительных данных, но основная нагрузка должна ложиться на локальные мощности.

## 2. Сравнение моделей эмбеддингов

Эмбеддинги преобразуют текст в числовые векторы для семантического поиска. Облачное решение — OpenAI Embeddings API (`text-embedding-ada-002`) — является золотым стандартом с точки зрения качества поиска и простоты использования. Скорость индексации ограничена только лимитами API. Однако, как и в случае с LLM, этот вариант неприменим из-за необходимости отправлять весь корпус текстов (21 000+ документов) во внешний сервис, что представляет собой массовую утечку данных.

Локальные модели семейства Sentence-Transformers, в частности `all-mpnet-base-v2` или `all-MiniLM-L6-v2`, предлагают качество семантического поиска, близкое к облачному эталону, особенно для технических текстов. Скорость создания индекса зависит от CPU/GPU: на современном процессоре с множеством ядер обработка тысяч документов может занять часы, что приемлемо для batch-обработки и инкрементальных обновлений (400 страниц в месяц). Стоимость владения — это единовременные затраты на вычислительные ресурсы сервера. Этот подход обеспечивает полную безопасность, так как тексты никогда не покидают периметр компании.

Для QuantumForge выбор очевиден: необходимо использовать локальные Sentence-Transformers модели. Они предоставляют необходимый баланс между качеством, безопасностью и контролем над затратами.

## 3. Сравнение векторных баз данных: ChromaDB vs FAISS

FAISS — это высокопроизводительная библиотека от Facebook AI Research для поиска ближайших соседей. Её главное преимущество — исключительная скорость поиска и индексации, достигнутая за счёт низкоуровневой оптимизации. Однако FAISS является именно библиотекой, а не готовой базой данных. Это означает, что разработчикам придётся самостоятельно реализовывать хранение метаданных (например, для фильтрации по роли пользователя или типу документа), механизмы persistence (сохранения индекса на диск) и сетевой API. Это увеличивает сложность внедрения и поддержки, создавая дополнительную инженерную нагрузку.

ChromaDB — это полноценная векторная база данных с открытым исходным кодом. Она предоставляет встроенную поддержку метаданных, что критически важно для кейса QuantumForge, где необходима фильтрация ответов для разработчиков, поддержки и менеджеров. ChromaDB автоматически управляет сохранением данных на диск и предлагает готовый HTTP API, что значительно упрощает интеграцию. Она поддерживает инкрементальное добавление документов, что идеально соответствует ежемесячному приросту в 400 страниц. Хотя чистая скорость поиска у ChromaDB может быть немного ниже, чем у FAISS, для объёма данных компании (десятки тысяч документов) и требований по времени ответа (несколько секунд) она более чем достаточна.

С точки зрения стоимости владения, оба решения являются open-source. Основные затраты связаны с инфраструктурой: для FAISS потребуется больше оперативной памяти для хранения индекса и метаданных, развёрнутых отдельно, в то время как ChromaDB, будучи более комплексным решением, может потребовать чуть больше ресурсов на одном сервере, но избавляет от затрат на разработку и поддержку недостающей функциональности.

Для QuantumForge, где критически важна готовность решения, встроенная фильтрация и простота интеграции с существующей микросервисной архитектурой, ChromaDB является предпочтительным выбором.

## Рекомендуемая архитектура

Учитывая требования безопасности и масштаб данных, рекомендуется полностью локальная архитектура на базе собственных серверов. Использование облачных вендоров (AWS, Azure) для управляемых Kubernetes-сервисов (EKS, AKS) допустимо только в качестве платформы оркестрации, при условии размещения в приватных сетях (VPC/VNet) и гарантий, что данные не покидают регион и не передаются другим сервисам провайдера. Однако, для максимального контроля развёртывание в собственном дата-центре компании предпочтительнее.

### Вариант 1: Продакшн-кластер (рекомендовано)

Для обслуживания 150 сотрудников с пиковой нагрузкой требуется кластер из специализированных серверов, подключённых высокоскоростной сетью.

| Роль | Аппаратная конфигурация | Программный стек | Сетевое подключение |
| :--- | :--- | :--- | :--- |
| **Узел LLM (GPU-сервер)** | 2x CPU (Xeon Gold или EPYC, 32+ ядер), 512 ГБ RAM, **4x NVIDIA L40S 48GB GPU**. Хранилище: 2x NVMe 3.84 ТБ RAID1. | Ollama или vLLM для serving моделей (Llama 3 70B 4-bit). Мониторинг: DCGM, Prometheus. | 2x 25 GbE порта, подключение к коммутатору ядра. |
| **Узел Vector DB & Embeddings** | 1x CPU (AMD EPYC 9354P, 32 ядер), **1 ТБ RAM**, 1x NVIDIA RTX A5000 24GB (опц.). Хранилище: 4x NVMe 7.68 ТБ RAID10. | ChromaDB (режим с persistence), Sentence-Transformers, FastAPI для сервиса эмбеддингов. | 2x 25 GbE порта. |
| **Узел ETL, API Gateway, Кэш** | 1x CPU (20-24 ядра), 256 ГБ RAM. Хранилище: 2x NVMe 1.92 ТБ. | Python ETL-пайплайны, Redis для кэша, NGINX/HAProxy, основной бэкенд на FastAPI. | 1x 25 GbE, 1x 10 GbE для клиентского трафика. |
| **Сетевая инфраструктура** | **Коммутатор ядра**: 100 GbE (например, Arista 7050X3). **Топология**: звезда. **Задержка**: <100 мкс. | Изоляция: отдельные VLAN для storage, management и application трафика. Шифрование: MACsec для защиты каналов связи. | |

**Преимущества:** Высокая производительность, отказоустойчивость, специализация узлов, полный контроль.
**Недостатки:** Высокие CAPEX, сложность администрирования.
**Ориентировочная стоимость:** ~$220,000 CAPEX + $1,500/мес OPEX.

### Вариант 2: Консолидированный продакшн-сервер

Для компаний, готовых принять риск единой точки отказа, можно рассмотреть один мощный сервер.

| Компонент | Конфигурация |
| :--- | :--- |
| **Корпус и питание** | 4U сервер с 1600W PSU. |
| **Процессоры** | 2x AMD EPYC 9474F (48 ядер) или Intel Xeon Gold 6430. |
| **Память** | 768 ГБ DDR5 ECC. |
| **Графические ускорители** | 2x NVIDIA RTX 6000 Ada 48GB. |
| **Хранилище** | Система: 2x NVMe 2TB RAID1. Данные: 4x SATA SSD 4TB RAID10. |
| **Сеть** | 2x 10 GbE порта. |

**Преимущества:** Снижение CAPEX (~$120,000), проще администрирование.
**Недостатки:** Нет отказоустойчивости, апгрейд требует простоя, производительность может стать узким местом.

### Вариант 3: Облачная инфраструктура на AWS (с оговорками)

Если принято решение использовать облако, развёртывание должно быть максимально изолированным.

| Компонент | AWS Сервис / Конфигурация | Примечания по безопасности |
| :--- | :--- | :--- |
| **Вычисления (LLM)** | Инстансы EC2 `g5.48xlarge` (8x A10G 24GB) или `p4d.24xlarge`. Автомасштабируемая группа. | Размещение в приватных сабнетах. Доступ только через балансировщик. |
| **Векторная БД и эмбеддинги** | Выделенные инстансы EC2 `r6i.16xlarge` (64 vCPU, 512 ГБ RAM) для ChromaDB. | Шифрование EBS томов с помощью KMS. Сетевые политики Security Groups. |
| **Оркестрация** | Amazon EKS (Kubernetes). | Использование приватных endpoint для EKS API. IAM-роли для сервисных аккаунтов. |
| **Сеть** | VPC с NAT Gateway для контролируемого исходящего трафика. | Все межсервисные коммуникации внутри VPC. Никаких данных не передаётся в другие сервисы AWS. |

**Преимущества:** Низкие начальные затраты, автоматическое масштабирование, использование экспертизы AWS.
**Недостатки:** Годовая стоимость может превысить CAPEX локального решения, остаются риски, связанные с доверием облачному провайдеру.

### Вариант 4: Тестовый стенд (1 сервер)

Для разработки, отладки промптов и пилотного тестирования с небольшой группой.

| Компонент | Конфигурация | Обоснование |
| :--- | :--- | :--- |
| **Корпус** | 4U (Supermicro или аналог) | Достаточно места для охлаждения GPU. |
| **CPU** | 2x Intel Xeon Silver 4316 (20 ядер) | Достаточно ядер для эмбеддингов и оркестрации. |
| **RAM** | 256 ГБ DDR4 ECC | Для одновременной работы LLM (~40 ГБ), ChromaDB и ОС. |
| **GPU** | 1x **NVIDIA RTX 6000 Ada 48GB** | Ключевой выбор: 48 ГБ памяти достаточно для Llama 3 70B в 4-bit. |
| **Хранилище** | 2x 1TB NVMe (система), 2x 4TB SATA SSD (данные) | Разделение для производительности и ёмкости. |
| **Сеть** | 2x 10 GbE | Для подключения к корпоративной сети. |

**Программный стек:** Docker Compose с Ollama (Llama 3 70B), ChromaDB, Sentence-Transformers и FastAPI-бэкендом.
**Назначение:** Тестирование полного пайплайна на 1,000-2,000 документах.
**Ориентировочная стоимость:** $25,000 - $30,000.

## Итоговые рекомендации

Учитывая строгие требования к безопасности конфиденциальных промышленных данных и необходимость соответствия SOC 2, **единственным жизнеспособным вариантом для QuantumForge является полностью локальное развёртывание**.

1.  **Векторная база данных:** **ChromaDB**. Выбор обусловлен критически важной необходимостью фильтрации по метаданным (ролям пользователей), наличию готового API для лёгкой интеграции в микросервисный стек компании и поддержке инкрементальных обновлений, что соответствует ежемесячному приросту документации.

2.  **LLM и эмбеддинги:** **Локальные модели**. Использование облачных API для основных компонентов генерации и поиска исключено из соображений безопасности. Начать следует с развёртывания локальных Sentence-Transformers и Llama 3/CodeLlama на тестовом стенде.

3.  **Инфраструктурная стратегия:** **Поэтапный переход от тестового стенда к продакшн-кластеру**.
    *   **Фаза 1 (месяцы 1-3):** Развёртывание и отладка системы на **тестовом стенде** (1 сервер с RTX 6000 Ada). Загрузка пилотного набора данных, обучение команды, сбор первых метрик.
    *   **Фаза 2 (месяцы 4-6):** Приобретение и развёртывание **продакшн-кластера** из трёх серверов (специализированные узлы LLM, Vector DB и шлюза). Перенос всех конфиденциальных данных, подключение основной массы пользователей.
    *   **Фаза 3 (месяцы 7-12):** Оптимизация, масштабирование и внедрение продвинутых функций (агенты, анализ пробелов в документации).

Данный подход минимизирует начальные риски, позволяет получить первые результаты и доказать ценность системы на тестовом стенде, прежде чем инвестировать в полноценный кластер. Это обеспечивает соблюдение всех требований безопасности при поступательном движении к цели — сокращению времени поиска информации и повышению эффективности работы 150 сотрудников QuantumForge Software.
